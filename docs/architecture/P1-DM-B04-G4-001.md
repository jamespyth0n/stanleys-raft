## 1. Purpose

This sub-anchor governs implementation and verification of the B04 integrated application workflow authorized under Gate 4 of P1-DM-B04-001.

Its purpose is to establish a working, testable application path connecting:

1. Model-assisted extraction.
2. Explicit candidate approval and trusted capture.
3. B03 persistence.
4. Retrieval of the persisted version.
5. Context assembly.
6. Provider-neutral response generation.
7. Construction of the existing B03 ModelResponseOutcome.
8. Accurate B04 reporting of success and partial failure.

The complete end-to-end integration test is a required Gate 4 implementation deliverable. It must be written and executed as part of Gate 4, not deferred to Gate 5.

This sub-anchor supplements the parent anchor and the Gate 4 implementation control plan. It does not replace either document.

## 4. Trust and approval boundary

Extraction proposes. The application validates. The Architect or authorized caller explicitly approves capture.

The existing sequence remains:

1. `extract(source_content=...)` produces validated ExtractionCandidate proposals.
2. Extraction does not persist anything.
3. A caller explicitly selects a candidate.
4. `capture_candidate(...)` receives the candidate and trusted source identity.
5. The application constructs the existing CaptureRequest.
6. Verification status is assigned as UNVERIFIED.
7. CaptureService delegates to B03 MemoryStore.
8. B03 returns CaptureResult.

The integrated workflow must not combine extraction and persistence into an implicit operation.

Trusted source identity, source type and source locator remain application/caller supplied. Model output cannot assign provenance or verification authority.

## 5. Workflow result contract

A B04-owned immutable `WorkflowResult` is authorized as the application-level container for integrated workflow reporting.

It must remain separate from B03 persistence contracts.

The proposed fields are:

| Field | Type / meaning |
|---|---|
| `success` | Boolean; complete response workflow succeeded |
| `capture_result` | Optional existing B03 CaptureResult |
| `retrieved_memory` | Optional existing B03 RetrievedMemory |
| `context_result` | Optional existing B04 ContextAssemblyResult |
| `response_outcome` | Optional existing B03 ModelResponseOutcome |
| `failed_stage` | Optional stable B04 stage identifier |
| `error_type` | Optional machine-readable error category |
| `error_message` | Optional diagnostic detail |

Requirements:

- Use an immutable dataclass consistent with existing B04 result structures.
- Preserve actual completed-stage results when a later stage fails.
- Do not claim a stage succeeded if it did not.
- Do not manufacture a CaptureResult, RetrievedMemory or ModelResponseOutcome.
- `None` means that the corresponding stage did not produce a result.
- A successful capture remains visible when retrieval or a later stage fails.
- A successful retrieval remains visible when context assembly or generation fails.
- A successful context result remains visible when generation fails.
- Error reporting must distinguish not-found from an exception raised by persistence.
- Do not add fields to B03 contracts to solve B04 reporting requirements.

Stage identifiers must be stable and documented. At minimum, the implementation must distinguish:

- `retrieval`
- `context_assembly`
- `response_generation`
- `response_outcome`

Capture remains an explicit preceding operation. A capture failure must not trigger retrieval or generation.

## 6. Response adapter boundary

The application must receive a response-generation adapter through explicit dependency injection.

The existing provider-neutral interface remains authoritative:

`generate(*, prompt: str, model_name: str | None = None) -> ModelResult`

Requirements:

- Reuse the existing ModelAdapter protocol.
- Reuse the existing ModelResult structure.
- Do not access ExtractionService private adapter state.
- Do not couple response generation to ExtractionService.
- Do not introduce provider-specific logic into application orchestration.
- The response adapter is independently injectable from the extraction adapter.
- MockModelAdapter must support deterministic response-generation tests.
- OllamaModelAdapter remains the existing provider implementation.
- A missing response adapter must produce an explicit failure, not false success.

No Ollama production modification is authorized by this sub-anchor.

## 7. Integrated response operation

The application must expose an explicit operation that continues from a successful B03 capture result.

Proposed public interface:

`respond_to_capture(*, capture_result, request_id, user_prompt, max_items, max_characters) -> WorkflowResult`

The implementation must reconcile exact imports and annotations against current source before editing.

### 7.1 Preconditions

- `capture_result` must be the existing B03 CaptureResult type.
- `request_id` must satisfy the existing B03 UUIDv4 contract.
- `user_prompt` must be a non-empty string.
- Context limits must follow the existing ContextAssembler contract.
- A response adapter must be configured.

Invalid input must not be represented as a successful workflow.

### 7.2 Required sequence

1. Retain the supplied CaptureResult.
2. Retrieve its `version_id` through RetrievalService.
3. Distinguish a returned `None` from a retrieval/persistence exception.
4. Assemble context using the existing ContextAssembler.
5. Preserve the existing content-only character accounting, input ordering and whole-record exclusion policy.
6. Generate a response through the injected ModelAdapter.
7. Construct the existing B03 ModelResponseOutcome.
8. Return WorkflowResult with accurate stage results.

The workflow must not bypass RetrievalService or ContextAssembler.

### 7.3 Context and prompt requirements

- Use the assembled ContextItem records as the response context.
- Preserve atom identity, version identity, content and provenance in the application result.
- The model prompt must contain the caller's user prompt and the assembled memory content.
- Include stable record identity in the prompt so the response context can be traced to the retrieved version.
- Delimit memory context clearly.
- Treat retrieved memory as reference material, not as instructions that can override application or system instructions.
- Do not claim that prompt wording proves semantic safety or resistance to prompt injection.
- Do not truncate memory records or silently bypass ContextAssembler limits.

If the captured version is excluded from the assembled context, do not generate a response that falsely implies the captured record was used. Return an explicit context-stage failure.

### 7.4 ModelResponseOutcome construction

Use the existing B03 contract without modification.

Populate:

| Field | Source |
|---|---|
| `request_id` | Caller-supplied UUIDv4 |
| `model_name` | ModelResult returned by the adapter |
| `response_text` | ModelResult returned by the adapter |
| `retrieved_version_ids` | Versions actually included in assembled context |
| `completed_at` | Application-generated timezone-aware UTC timestamp |
| `success` | Actual response-generation result |
| `error_type` | Model/application error category, or None on success |

Do not report every retrieved version as used if it was excluded from context.

A returned unsuccessful ModelResult must not be converted into a successful outcome.

If an adapter raises unexpectedly and no valid ModelResult exists, retain the earlier successful stage results in WorkflowResult and report the generation failure. Do not fabricate a ModelResponseOutcome.

If an outcome cannot be constructed because its contract validation fails, report an explicit response-outcome construction failure.

## 8. Failure and partial-success requirements

The implementation must preserve the following distinctions.

| Failure point | Required reporting |
|---|---|
| Capture fails | No retrieval, context assembly or generation |
| Retrieved version not found | `memory_not_found`; capture result retained |
| Retrieval raises | Explicit retrieval failure; capture result retained |
| Context assembly fails | Capture and retrieved memory retained |
| Captured version excluded from context | Explicit context failure; no generation |
| Response adapter missing | Explicit response-generation failure |
| Adapter returns unsuccessful ModelResult | Failed response outcome when validly constructible |
| Adapter raises unexpectedly | Explicit response-generation failure; no fabricated outcome |
| Adapter returns invalid result type | Explicit response-generation failure |
| Outcome contract construction fails | Explicit response-outcome failure |
| All stages succeed | Complete WorkflowResult and successful ModelResponseOutcome |

Requirements:

- Do not collapse not-found and persistence failure.
- Do not swallow exceptions and return success.
- Do not lose successful earlier-stage results.
- Do not automatically retry capture.
- Do not duplicate captures.
- Do not add response persistence.
- Do not misrepresent partial success as full success.

## 9. End-to-end acceptance test

A dedicated test module must be created:

`tests/test_b04_workflow_integration.py`

This test is part of Gate 4 implementation and acceptance. It is not optional and must not be postponed to Gate 5.

### 9.1 Complete workflow test

At minimum, one deterministic integration test must exercise the complete sequence:

1. Initialize a temporary SQLite database using the authoritative B03 schema.
2. Construct a real B03 MemoryStore against that temporary database.
3. Inject a deterministic extraction adapter.
4. Extract a candidate from source content.
5. Verify extraction alone does not persist.
6. Explicitly approve and capture the candidate using trusted source identity.
7. Verify the resulting CaptureResult.
8. Inject an independent deterministic response adapter.
9. Invoke the integrated response operation using the CaptureResult.
10. Retrieve the persisted version through the application.
11. Assemble context.
12. Generate a response.
13. Construct ModelResponseOutcome.
14. Verify WorkflowResult and ModelResponseOutcome.
15. Verify atom/version identity, content, provenance and UNVERIFIED status.
16. Verify retrieved_version_ids contains the version actually used.
17. Verify both model adapters received their expected prompts.
18. Verify no response was persisted.

The test must use temporary storage only. It must never point at the protected external Satori rag.db.

### 9.2 Failure-path tests

The new test module must also cover:

- Capture failure prevents downstream processing.
- Retrieval not-found.
- Retrieval exception.
- Context assembly failure.
- Captured version excluded by context limits.
- Missing response adapter.
- ModelResult failure.
- Unexpected adapter exception.
- Invalid adapter result.
- Outcome construction failure, where it can be tested deterministically.

Tests may use controlled spies or mocks for isolated failure paths. The primary successful workflow test must use real temporary B03 persistence.

### 9.3 Existing tests

Preserve existing Gate 2 and Gate 3 tests unless a demonstrated defect requires a separately authorized change.

Do not rewrite existing tests merely to accommodate the new workflow.
