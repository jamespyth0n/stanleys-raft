## 1. Purpose

Define sufficiently comprehensive data structures and contracts for Dynamic Memory.

The system must support the P1 memory roundtrip while preserving a coherent path for future capabilities.

The schema and contracts must describe not only what P1 implements, but also the legitimate extension points that later development may require.

## 2. Critical design principle — Contract sufficiency

**Build lean. Design sufficiently. Document ahead. Implement progressively.**

Lean implementation does not mean an unnecessarily minimal schema or incomplete contracts.

Three separate dimensions govern development:

| Dimension | Requirement |
|---|---|
| Architecture and contracts | Sufficiently comprehensive, coherent and extensible |
| P1 implementation | Only the functionality required for the working prototype |
| P1 testing | Test implemented behavior, integrity constraints and critical interfaces |

A capability may be represented in the architecture or reserved in a contract without being implemented or tested in P1.

### 2.1 Mandatory distinctions

- **Defined:** Its purpose, data meaning and interface are documented.
- **Reserved:** An extension point or placeholder exists for future use.
- **Implemented:** Working application functionality exists.
- **Tested:** Evidence demonstrates the implemented behavior.
- **Deferred:** Intentionally outside the current implementation scope.

These states must not be conflated.

A reserved capability is not an implemented feature. A documented interface is not evidence of operational functionality.

### 2.2 Design safeguards

1. Do not omit a legitimate future requirement merely because P1 does not exercise it.
2. Do not invent fields without a defined meaning or purpose.
3. Prefer explicit extension points over speculative complexity.
4. Preserve identity, lineage, provenance and integrity across future extensions.
5. Do not make future functionality a dependency of the P1 working prototype.
6. Changes to ratified architecture or implementation scope remain subject to Architect authorization.

## 3. P1 core data model

Database: `data\dm_memory.db`

The existing Satori `rag.db` remains protected and untouched.

### 3.1 `atoms` — stable knowledge identity

Represents the identity and lineage of a knowledge item.

| Field | Type | Purpose |
|---|---|---|
| `atom_id` | TEXT | Primary key; UUIDv4 |
| `created_at` | TEXT | UTC creation timestamp |

Future lifecycle metadata may be introduced through a controlled schema revision.

### 3.2 `atom_versions` — immutable knowledge assertions

| Field | Type | Purpose |
|---|---|---|
| `version_id` | TEXT | Primary key; UUIDv4 |
| `atom_id` | TEXT | Foreign key to atoms |
| `version_no` | INTEGER | Sequential within atom |
| `knowledge_type` | TEXT | Controlled classification |
| `assertion` | TEXT | Human-readable assertion |
| `epistemic_status` | TEXT | Nature of the assertion |
| `verification_status` | TEXT | Verification state |
| `content_hash` | TEXT | SHA-256 content identity |
| `created_at` | TEXT | UTC storage timestamp |
| `valid_from` | TEXT | Optional applicability start |
| `valid_until` | TEXT | Optional applicability end |
| `supersedes_version_id` | TEXT | Optional prior version reference |

Rules:

- A new revision creates a new `version_id`.
- Assertion content is immutable after acceptance into storage.
- `(atom_id, version_no)` must be unique.
- A superseding version must belong to the same atom lineage.
- A content hash identifies content; it does not establish authenticity or truth.

### 3.3 `provenance` — source attribution

| Field | Type | Purpose |
|---|---|---|
| `provenance_id` | TEXT | Primary key; UUIDv4 |
| `version_id` | TEXT | Foreign key to atom_versions |
| `source_kind` | TEXT | Controlled source category |
| `source_id` | TEXT | System-generated source identifier |
| `source_locator` | TEXT | Optional location within source |
| `captured_at` | TEXT | UTC capture timestamp |

Future provenance extensions should support:

- Multiple sources for one assertion.
- Source documents and conversation references.
- Exact source passages or location markers.
- Extraction method and originating system.
- Capture time versus original source time.
- Source revision and lineage.
- Provenance chains and transformation history.

The model cannot invent trusted source identifiers. Missing provenance must be explicit.

### 3.4 `atom_version_relations` — explicit semantic relationships

| Field | Type | Purpose |
|---|---|---|
| `from_version_id` | TEXT | Source version |
| `to_version_id` | TEXT | Target version |
| `relation_type` | TEXT | Controlled relationship |
| `created_at` | TEXT | UTC creation timestamp |

P1 relationship type:

- `disputes`

The contract must permit future relationship types without confusing semantic relationships with coincidental co-occurrence.

Future relationship vocabulary may include:

- supports
- contradicts
- qualifies
- derives_from
- depends_on
- explains
- exemplifies
- references
- equivalent_to

These are reserved candidates, not automatically accepted semantics.

Important distinction:

- `supersedes` — revision lineage.
- `disputes` — semantic disagreement.
- `supports` — evidential or logical support.
- `co_occurs_with` — observed joint activity, not proof of semantic relationship.

Contradictory assertions may coexist. P1 does not automatically resolve conflicts.

### 3.5 `activity_events` — minimal execution evidence

| Field | Type | Purpose |
|---|---|---|
| `event_id` | TEXT | Primary key; UUIDv4 |
| `event_type` | TEXT | Controlled event category |
| `occurred_at` | TEXT | UTC timestamp |
| `outcome` | TEXT | Execution result |
| `atom_id` | TEXT | Optional atom reference |
| `version_id` | TEXT | Optional version reference |
| `details_json` | TEXT | Optional structured details |

P1 events include capture, retrieval, context assembly and model response outcomes.

Future activity contracts may support:

- Retrieval paths and selected sources.
- Ranking and relevance evidence.
- Verification actions.
- User corrections and feedback.
- Co-occurrence observations.
- Discovery paths.
- Calibration measurements.

P1 records minimal outcome evidence only. Advanced analytics remain deferred.

## 4. Reserved architectural extensions

The following concepts must be documented as legitimate future extension points. They do not become P1 implementation requirements.

### 4.1 Entities and identity resolution

Future entity contracts should support:

- Stable entity identifiers.
- Entity types and names.
- Aliases and alternate names.
- Entity references from knowledge atoms.
- Identity resolution evidence.
- Distinction between identity equivalence and similarity.

Candidate structures: `entities`, `atom_entity_refs`.

### 4.2 Tags and classification

Future classification contracts should support:

- Tags at atom and relationship levels.
- Controlled and user-defined vocabularies.
- Hierarchical classifications.
- Taxonomy versioning.
- Classification provenance.
- Distinction between classification and semantic relationship.

Candidate structure: `atom_tags`, with a future controlled vocabulary registry.

Tags are discovery and classification aids, not proof of meaning.

### 4.3 Knowledge relationships

Future relationship contracts should support:

- Typed semantic relationships.
- Directionality.
- Relationship evidence.
- Confidence or qualification where justified.
- Relationship provenance.
- Temporal validity.
- Human verification and lifecycle.

Do not equate shared tags, statistical similarity or joint retrieval with a verified semantic relationship.

### 4.4 Temporal and lifecycle metadata

Future contracts should distinguish:

- When information was created.
- When it was captured.
- When it became applicable.
- When it ceased to be applicable.
- When it was superseded.
- When it was verified or challenged.

Historical versions must remain traceable.

### 4.5 Confidence and verification history

Future contracts should permit:

- Verification records.
- Verification source and method.
- Confidence assessments with defined semantics.
- Human review and correction.
- Conflicting evidence.
- Verification history over time.

Confidence must never be treated as an automatic measure of truth.

### 4.6 Embeddings and model projections

Future contracts should support optional model-derived representations:

- Exact `version_id` association.
- Embedding model and version.
- Dimensionality and representation metadata.
- Generation timestamp.
- Regeneration and invalidation.
- Separation from canonical assertion content.

Embeddings are derived projections, not authoritative knowledge.

### 4.7 Intelligence and calibration outputs

Future contracts may support:

- Relationship candidates.
- Pattern and trend observations.
- Relevance assessments.
- Retrieval-quality evaluations.
- Missing-context observations.
- Recommendation records.
- Calibration and feedback history.

These outputs must retain provenance and distinguish observed facts from inferred candidates and recommendations.

No automatic promotion of generated candidates into accepted knowledge.

## 5. Pydantic contracts

Pydantic V2 is the structural contract authority.

Minimum P1 contracts:

1. Capture request.
2. Capture result.
3. Retrieved memory.
4. Provenance record.
5. Relationship record.
6. Activity event.
7. Context item.
8. Model response outcome.

The contract architecture must also provide a clear extension strategy for future entities, tags, verification records, temporal metadata, embeddings and intelligence outputs.

Rules:

- Python generates UUIDs.
- Python attaches trusted provenance.
- Pydantic validates structural and type constraints.
- Application logic validates semantic and cross-field rules.
- SQLite enforces persistence integrity.
- Model-generated content remains untrusted until accepted by the application.

Pydantic validation does not establish semantic truth or source authenticity.

## 6. Controlled vocabularies

### `knowledge_type`

- `fact`
- `observation`
- `preference`
- `concept`
- `question`
- `intention`
- `procedure`
- `hypothesis`
- `conclusion`

### `epistemic_status`

- `asserted`
- `observed`
- `inferred`
- `hypothesized`
- `concluded`

### `verification_status`

- `unverified`
- `verified`
- `challenged`

These describe different dimensions and must remain separate.

Future vocabulary additions must be versioned and governed. Unknown values must not silently acquire unintended meanings.

## 7. Database integrity and evolution

Mandatory principles:

- Enable `PRAGMA foreign_keys=ON` on every database connection.
- Use parameterized SQL.
- Define transaction boundaries.
- Commit successful captures.
- Roll back failed transactions.
- Verify persistence after restart.
- Preserve immutable assertion versions.
- Maintain referential integrity.
- Keep the protected Satori database untouched.

Future schema changes must use controlled migrations.

Migrations should preserve existing records, identifiers, provenance and historical meaning. A schema upgrade must not silently rewrite knowledge.

The contract should distinguish required fields, optional fields, reserved extensions and versioned additions.

## 8. P1 implementation boundary

P1 implements only what is needed for the smallest functional memory roundtrip.

P1 implementation includes:

- Stable atom identity.
- Immutable assertion versions.
- Essential knowledge classification.
- Verification and epistemic status.
- Source provenance.
- Basic revision lineage.
- Minimal explicit dispute support where needed.
- Activity outcome records.
- Validated context assembly.

Future entities, taxonomies, richer relationship semantics, analytics, embeddings and calibration may be documented or reserved but are not required to operate the P1 prototype.

## 9. Testing boundary

P1 testing must establish:

- Valid capture and persistence.
- Stable identity and version lineage.
- Provenance preservation.
- Foreign-key enforcement.
- Transaction integrity.
- Restart persistence.
- Retrieval and context assembly.
- Correct separation of superseding and disputing.
- Contract validation for implemented behavior.

Reserved future capabilities do not require operational tests in P1.

Their documentation must nevertheless be sufficiently clear that future implementation does not require reconstructing their intended purpose from memory.

## 10. B03 deliverables

1. Sufficiently comprehensive logical data model.
2. P1 SQLite DDL.
3. Pydantic contract definitions.
4. Controlled vocabulary definitions.
5. Identity, provenance and relationship invariants.
6. Future extension registry or documented extension points.
7. Schema evolution and migration principles.
8. Bounded component and integrity test specifications.

## 11. Acceptance criteria

B03 is ready for Architect ratification when:

- P1 data requirements are fully defined.
- Legitimate future extension points are documented.
- Contract sufficiency is not confused with implementation scope.
- Identity, version lineage and provenance are unambiguous.
- Semantic relationships are distinct from tags and co-occurrence.
- Temporal, epistemic and verification concepts are distinct.
- Database and Pydantic responsibilities are clear.
- Schema evolution is addressed.
- P1 remains independently functional without deferred capabilities.
- No unnecessary infrastructure or hidden P2 dependency has been introduced.
