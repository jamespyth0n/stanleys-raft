## 1. Purpose

Define the technical database schema, application contracts, integrity rules and verification requirements for P1-DM-B03.

B03 establishes the data foundation for the P1 Dynamic Memory roundtrip:

1. Capture a memory.
2. Persist it with stable identity and provenance.
3. Preserve its content as an immutable version.
4. Retrieve it after application restart.
5. Assemble retrieved information into model context.
6. Record a minimal execution outcome.

This package translates the ratified design into an implementable technical specification.

It does not authorize implementation of deferred P2 capabilities.

## 2. Design principles

1. **Stable identity, evolving versions.** An atom has a persistent identity. Each revision receives a new immutable version.
2. **Provenance is mandatory.** Stored memory must retain traceable source information.
3. **Provenance is not proof of truth.** Source traceability and factual verification remain separate.
4. **Append, don't overwrite.** A changed assertion creates a new version.
5. **Relationships are explicit.** P1 supports the `disputes` relationship. A general predicate registry is reserved for future development.
6. **Contracts precede execution.** Pydantic models define the application-facing data contracts.
7. **Structural validity is not semantic accuracy.** Passing validation does not establish that an assertion is true.
8. **Keep P1 lean.** No graph database, vector database, dynamic registry service or autonomous knowledge promotion.

## 3. P1 persistence model

### 3.1 Core tables

| Table | Responsibility |
|---|---|
| `atoms` | Stable logical identity |
| `atom_versions` | Immutable assertion content and revisions |
| `provenance` | Source traceability for a specific version |
| `atom_version_relations` | Explicit relationships between versions |
| `activity_events` | Minimal record of relevant system activity |

### 3.2 Identity and version rules

- `atom_id`: UUIDv4, stable across revisions.
- `version_id`: UUIDv4, unique to each immutable version.
- `version_no`: sequential within an atom, beginning at 1.
- `content_hash`: SHA-256 of the exact persisted assertion string encoded as UTF-8.
- A revision retains the original `atom_id`, receives a new `version_id` and increments `version_no`.
- `supersedes_version_id` must refer to an earlier version belonging to the same atom.
- No implicit normalization or rewriting of assertion content occurs during hashing.

### 3.3 Controlled vocabularies

**knowledge_type**

- `fact`
- `observation`
- `preference`
- `concept`
- `question`
- `intention`
- `procedure`
- `hypothesis`
- `conclusion`

**epistemic_status**

- `asserted`
- `observed`
- `inferred`
- `hypothesized`
- `concluded`

**verification_status**

- `unverified`
- `verified`
- `challenged`

These fields describe different dimensions. For example, `knowledge_type=fact` does not mean `verification_status=verified`.

## 4. SQLite DDL

Target database: `data/dm_memory.db`

The application must enable foreign-key enforcement on every database connection.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS atoms (
    atom_id TEXT PRIMARY KEY,
    created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS atom_versions (
    version_id TEXT PRIMARY KEY,
    atom_id TEXT NOT NULL,
    version_no INTEGER NOT NULL CHECK (version_no >= 1),

    content TEXT NOT NULL,
    content_hash TEXT NOT NULL
        CHECK (
            length(content_hash) = 64
            AND content_hash NOT GLOB '*[^0-9a-f]*'
        ),

    knowledge_type TEXT NOT NULL CHECK (
        knowledge_type IN (
            'fact', 'observation', 'preference',
            'concept', 'question', 'intention',
            'procedure', 'hypothesis', 'conclusion'
        )
    ),

    epistemic_status TEXT NOT NULL CHECK (
        epistemic_status IN (
            'asserted', 'observed', 'inferred',
            'hypothesized', 'concluded'
        )
    ),

    verification_status TEXT NOT NULL CHECK (
        verification_status IN (
            'unverified', 'verified', 'challenged'
        )
    ),

    valid_from TEXT,
    valid_until TEXT,

    created_at TEXT NOT NULL,
    supersedes_version_id TEXT,

    UNIQUE (atom_id, version_no),
    UNIQUE (atom_id, version_id),

    FOREIGN KEY (atom_id)
        REFERENCES atoms(atom_id),

    FOREIGN KEY (atom_id, supersedes_version_id)
        REFERENCES atom_versions(atom_id, version_id),

    CHECK (
        supersedes_version_id IS NULL
        OR supersedes_version_id <> version_id
    ),

    CHECK (
        valid_until IS NULL
        OR valid_from IS NOT NULL
        OR valid_until IS NOT NULL
    )
);

CREATE TABLE IF NOT EXISTS provenance (
    provenance_id TEXT PRIMARY KEY,
    version_id TEXT NOT NULL,

    source_type TEXT NOT NULL,
    source_id TEXT NOT NULL,
    source_locator TEXT,

    source_created_at TEXT,
    captured_at TEXT NOT NULL,
    source_content_hash TEXT,

    FOREIGN KEY (version_id)
        REFERENCES atom_versions(version_id)
);

CREATE INDEX IF NOT EXISTS idx_atom_versions_atom
    ON atom_versions(atom_id, version_no);

CREATE INDEX IF NOT EXISTS idx_provenance_version
    ON provenance(version_id);

CREATE TABLE IF NOT EXISTS atom_version_relations (
    relation_id TEXT PRIMARY KEY,

    from_version_id TEXT NOT NULL,
    to_version_id TEXT NOT NULL,

    relation_type TEXT NOT NULL CHECK (
        relation_type IN ('disputes')
    ),

    created_at TEXT NOT NULL,

    FOREIGN KEY (from_version_id)
        REFERENCES atom_versions(version_id),

    FOREIGN KEY (to_version_id)
        REFERENCES atom_versions(version_id),

    CHECK (from_version_id <> to_version_id)
);

CREATE INDEX IF NOT EXISTS idx_relations_from
    ON atom_version_relations(from_version_id);

CREATE INDEX IF NOT EXISTS idx_relations_to
    ON atom_version_relations(to_version_id);

CREATE TABLE IF NOT EXISTS activity_events (
    event_id TEXT PRIMARY KEY,

    event_type TEXT NOT NULL,
    occurred_at TEXT NOT NULL,

    atom_id TEXT,
    version_id TEXT,

    details_json TEXT,

    FOREIGN KEY (atom_id, version_id)
        REFERENCES atom_versions(atom_id, version_id),

    CHECK (
        (atom_id IS NULL AND version_id IS NULL)
        OR
        (atom_id IS NOT NULL AND version_id IS NOT NULL)
    )
);

CREATE INDEX IF NOT EXISTS idx_activity_occurred
    ON activity_events(occurred_at);

CREATE INDEX IF NOT EXISTS idx_activity_atom
    ON activity_events(atom_id, version_id);
```

### DDL implementation notes

- The composite foreign key on `atom_versions` enforces same-atom revision lineage.
- The composite foreign key on `activity_events` ensures a referenced version belongs to the stated atom.
- Multiple provenance records may reference one version.
- The P1 relationship vocabulary is deliberately limited to `disputes`.
- `details_json` is validated by Python. P1 does not depend on SQLite JSON extensions.
- Timestamp format and temporal ordering are enforced by application validation.
- The `content_hash` SQL constraint checks format only. Python must calculate and verify the actual SHA-256 value.
- The temporal fields are optional. When both are supplied, `valid_until` must not precede `valid_from`.

## 5. Immutability and revision handling

### 5.1 Append-only version records

Accepted version records must not be modified or deleted.

```sql
CREATE TRIGGER IF NOT EXISTS prevent_atom_version_update
BEFORE UPDATE ON atom_versions
BEGIN
    SELECT RAISE(ABORT, 'Atom versions are immutable');
END;

CREATE TRIGGER IF NOT EXISTS prevent_atom_version_delete
BEFORE DELETE ON atom_versions
BEGIN
    SELECT RAISE(ABORT, 'Atom versions are immutable');
END;
```

A revision is created by inserting a new row, not updating the previous version.

The application must also enforce this rule. Database triggers provide an additional integrity barrier; they do not replace application-level controls.

### 5.2 Revision procedure

1. Identify the existing `atom_id`.
2. Read the latest version.
3. Create a new `version_id`.
4. Increment `version_no`.
5. Set `supersedes_version_id` to the previous version.
6. Calculate the new content hash.
7. Insert the new version and its provenance within a transaction.
8. Preserve the prior version unchanged.

A revision does not automatically establish that the earlier assertion was false.

## 6. Pydantic application contracts

Pydantic V2 is the authoritative application contract layer.

The following eight contracts are required.

| Contract | Purpose |
|---|---|
| `CaptureRequest` | Incoming memory capture |
| `CaptureResult` | Confirmation of persisted capture |
| `RetrievedMemory` | Retrieved memory with identity and provenance |
| `ProvenanceRecord` | Source traceability |
| `RelationshipRecord` | Explicit relationship |
| `ActivityEvent` | Minimal activity record |
| `ContextItem` | Memory selected for model context |
| `ModelResponseOutcome` | Outcome returned by the model adapter |

### 6.1 Contract implementation skeleton

```python
from datetime import datetime, timezone
from enum import StrEnum
from hashlib import sha256
from typing import Any
from pydantic import BaseModel, ConfigDict, Field, model_validator


class KnowledgeType(StrEnum):
    FACT = "fact"
    OBSERVATION = "observation"
    PREFERENCE = "preference"
    CONCEPT = "concept"
    QUESTION = "question"
    INTENTION = "intention"
    PROCEDURE = "procedure"
    HYPOTHESIS = "hypothesis"
    CONCLUSION = "conclusion"


class EpistemicStatus(StrEnum):
    ASSERTED = "asserted"
    OBSERVED = "observed"
    INFERRED = "inferred"
    HYPOTHESIZED = "hypothesized"
    CONCLUDED = "concluded"


class VerificationStatus(StrEnum):
    UNVERIFIED = "unverified"
    VERIFIED = "verified"
    CHALLENGED = "challenged"


class Contract(BaseModel):
    model_config = ConfigDict(extra="forbid")


class ProvenanceRecord(Contract):
    provenance_id: str
    version_id: str
    source_type: str
    source_id: str
    source_locator: str | None = None
    source_created_at: datetime | None = None
    captured_at: datetime
    source_content_hash: str | None = None


class CaptureRequest(Contract):
    content: str = Field(min_length=1)
    knowledge_type: KnowledgeType
    epistemic_status: EpistemicStatus
    verification_status: VerificationStatus = (
        VerificationStatus.UNVERIFIED
    )
    source_type: str
    source_locator: str | None = None
    valid_from: datetime | None = None
    valid_until: datetime | None = None

    @model_validator(mode="after")
    def validate_interval(self):
        if (
            self.valid_from is not None
            and self.valid_until is not None
            and self.valid_until < self.valid_from
        ):
            raise ValueError("valid_until precedes valid_from")
        return self


class CaptureResult(Contract):
    atom_id: str
    version_id: str
    version_no: int = Field(ge=1)
    content_hash: str
    persisted_at: datetime
    provenance_ids: list[str]


class RetrievedMemory(Contract):
    atom_id: str
    version_id: str
    version_no: int
    content: str
    content_hash: str
    knowledge_type: KnowledgeType
    epistemic_status: EpistemicStatus
    verification_status: VerificationStatus
    created_at: datetime
    provenance: list[ProvenanceRecord]


class RelationshipRecord(Contract):
    relation_id: str
    from_version_id: str
    to_version_id: str
    relation_type: str
    created_at: datetime


class ActivityEvent(Contract):
    event_id: str
    event_type: str
    occurred_at: datetime
    atom_id: str | None = None
    version_id: str | None = None
    details: dict[str, Any] | None = None

    @model_validator(mode="after")
    def validate_reference_pair(self):
        if (self.atom_id is None) != (self.version_id is None):
            raise ValueError(
                "atom_id and version_id must be supplied together"
            )
        return self


class ContextItem(Contract):
    atom_id: str
    version_id: str
    content: str
    provenance: list[ProvenanceRecord]


class ModelResponseOutcome(Contract):
    request_id: str
    model_name: str
    response_text: str
    retrieved_version_ids: list[str]
    completed_at: datetime
    success: bool
    error_type: str | None = None


def calculate_content_hash(content: str) -> str:
    return sha256(content.encode("utf-8")).hexdigest()
```

### 6.2 Contract implementation requirements

The skeleton establishes field intent and structural boundaries. Before acceptance, implementation must additionally verify:

- UUID formatting for generated identifiers.
- Timezone-aware timestamps, normalized to UTC for persistence.
- Hash equality against the exact persisted content.
- Relationship type membership in the P1 allowlist.
- Provenance and version references exist.
- Revision lineage and sequential version number.
- Validity interval ordering.
- Activity reference integrity.
- JSON serialization and deserialization of activity details.
- Model outcome references correspond to the retrieved context manifest.

The persistence layer generates identifiers and hashes. The LLM must not be trusted to supply authoritative IDs or content hashes.

### 6.3 Model Response Outcome — Persistence Boundary (F-04 Clarification)

`ModelResponseOutcome` is an application-level contract returned by the model adapter. Its inclusion among the eight required Pydantic contracts does not establish a requirement for dedicated SQLite persistence.

**P1/B03 requirements:**

1. Implement and structurally validate `ModelResponseOutcome` using Pydantic V2.
2. Preserve its defined fields and reject unexpected fields.
3. Ensure authoritative identifiers and timestamps are generated or validated by the application, not trusted to the LLM.
4. Validate that `retrieved_version_ids` correspond to the version identifiers in the context manifest supplied to the model.
5. Preserve minimal execution activity evidence through the existing `activity_events` mechanism where applicable.

**Explicit exclusions:**

- No dedicated model-response persistence table.
- No requirement to persist complete model response text in SQLite.
- No expansion of the five-table B03 schema solely to accommodate this contract.

**Verification boundary:**

B03 verifies the contract's structural behavior. Context-manifest correspondence and full model-adapter integration are verified at the B05 roundtrip acceptance boundary.

**Disposition:** F-04 is not a B03 persistence defect. The absence of a dedicated `ModelResponseOutcome` persistence method is intentional under the ratified design and does not block B03 completion.

## 7. Contract boundaries

The following responsibilities remain separate:

| Layer | Responsibility |
|---|---|
| Pydantic | Structural validation and typed contracts |
| Python application | Semantic checks, hashing, IDs, timestamps and business rules |
| SQLite | Persistence, uniqueness, foreign keys and database constraints |
| Retrieval | Selecting stored versions and their provenance |
| Context assembler | Preparing validated model context |
| LLM | Interpreting supplied context and generating a response |

Passing Pydantic validation does not prove truth, source authenticity, semantic correctness or authorization.

## 8. Transaction and integrity rules

### Capture transaction

A capture must not leave a partially persisted memory.

1. Begin transaction.
2. Insert stable atom identity.
3. Insert immutable version.
4. Insert associated provenance.
5. Insert minimal activity event.
6. Commit.

On failure, roll back the local transaction.

### Revision transaction

1. Read the current version.
2. Validate the proposed revision.
3. Insert the new version.
4. Insert new provenance.
5. Record the revision event.
6. Commit.

Previous versions remain intact.

### General rules

- Use parameterized SQL exclusively.
- Enable foreign keys on every connection.
- Use explicit transaction boundaries.
- Never silently overwrite accepted assertion content.
- Never treat provenance as verification.
- Do not silently resolve contradictions.
- Preserve disputed assertions and their evidence.
- Local SQLite atomicity does not guarantee atomicity across external systems.

## 12. Scope protection

B03 does not authorize:

- A graph database or vector database.
- A dynamic predicate registry service.
- Automated knowledge extraction or distillation.
- Autonomous acceptance or promotion of memories.
- Advanced semantic retrieval or reranking.
- Co-occurrence analytics or discovery-path processing.
- Advanced calibration or recommendation engines.
- Arbitrary LLM-generated Python or SQL.
- Changes to the protected Satori `rag.db`.

The P1 database remains `data/dm_memory.db`.
